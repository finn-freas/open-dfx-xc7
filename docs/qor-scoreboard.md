## Method

- Machine: Intel(R) Core(TM) 7 240H, 16 hardware threads; the open flow runs in WSL2 with 11.7 GB, Vivado 2025.2 on Windows on the same CPU. Vivado runs with its default thread count (`general.maxThreads` = 2, confirmed per run in result.txt and by place_design's "maximum of 2 CPUs"); yosys and nextpnr run single-threaded. Other agents' jobs shared the machine. Build time is therefore given three ways: wall clock (Vivado: the start-period run; open flow: median over the seeds of wall clock minus the time queued for a nextpnr slot in ofx/npwait.sh, which is not tool time), CPU seconds (Vivado: the process's TotalProcessorTime from Windows; open flow: user + system of the whole build from `/usr/bin/time`), and the WSL 1-minute load average during the open runs. CPU seconds are not inflated by waiting for a core, so they are the load-robust check; g build time uses the wall clock.
- Every design builds from the same RTL in both tools. A wrapped design is the upstream core inside `suite_top`: its inputs come from a 32-bit LFSR shift chain, its outputs are registered and XOR-reduced to one pin, so nothing is optimised away and the I/O count fits any package. Native designs (fir, bram, rv_big) use their own top.
- Vivado alone: `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream`, default strategies. Fmax sweep: run at the design's start period, then at the achieved period (period - WNS), up to 3 runs; Fmax = max over runs of 1000 / (period - WNS), Vivado's timer.
- Open flow runs: 3 seeds at the design's start period (the same number of runs as Vivado's sweep). A period sweep does not work for nextpnr-xilinx: its placer and router weight paths by criticality relative to the worst slack, so the target period does not change the result (aes at 6 ns and at 11.08 ns gave bit-identical FASM, 2026-11-08); seeds are the only knob that changes the result.
- Open flow: `flow/build_openxc7.py` (the plain `ofx build` flow: yosys `synth_xilinx -flatten -abc9`, nextpnr-xilinx, fasm2frames, xc7frames2bit). "ours, Vivado timer" (placed mode, exact import) is Vivado's timer on the open flow's implementation: nextpnr's physical netlist (its feed-through LUT1s and split CARRY4s included) exported by flow/xroute.py, every cell fixed at nextpnr's BEL, LUTRAM macros placed sub-cell by sub-cell, LUT pins locked as nextpnr used them; Vivado then only routes (`route_design`) and times. One Vivado run per seed at the period nextpnr reported for that seed, best over the seeds. Cells place_cell refuses are left to Vivado and counted. This is the like-for-like Fmax; where it is missing g Fmax falls back to the nextpnr timer and the table says so. An earlier import (yosys-netlist cells only, Vivado's LUT pins and LUTRAM sites) read 7-21 % optimistic on rv_soc and is not used.
- Area: LUT (logic LUTs), FF, BRAM (36 Kb equivalents), DSP after implementation (Vivado: report_utilization; open: cell counts of the yosys netlist). Power: Vivado `report_power` (vectorless defaults) and `ofx power` (the open estimate); `-` where the open power model is not installed.
- Placement quality, computed the same way for both tools' implementations at the start period: HPWL = sum over signal nets (no global clocks, no constants) of the half-perimeter of the nets' sites in prjxray tile-grid units; routed wirelength = used pips in INT tiles; congestion = peak and 99th-percentile used pips per INT tile.
- Score: per metric a goodness g (> 1 = open flow better): Fmax ours/Vivado; area = geometric mean of Vivado/ours over LUT, FF, BRAM, DSP; power Vivado/ours; build time Vivado/ours (total wall clock); routability Vivado/ours routed INT pips (0 if the open build failed). Weights: fmax 1, area 1, power 1, build_time 1, routability 1 (equal, user 2026-11-06). Overall = weighted geometric mean over the metrics present; verdict better if >= 1.05, on par if >= 0.95, else worse.

## Running it, and quick runs of a variant

- Full scoreboard: `python3 flow/qor_suite.py open --run` (3 seeds per design), `vivado --modes free --run` (Vivado alone), `vivado --modes placed --run` (Vivado timer on every open run), `report --run`. Finished runs are cached and skipped. nextpnr runs only through ofx/npwait.sh with OFX_MAX_NEXTPNR=2; every Vivado invocation (one per design) takes a slot with vivado/vivado_slot.sh `vivado_acquire` and releases it after.
- Quick mode (`--quick`): designs rv_big, serv, aes, sha256, bram, axi_xbar, seed 1, start period, one Vivado run. Variant runs keep their results apart from base under a name (`--variant NAME`, same as `--label`):

```
python3 flow/qor_suite.py open   --quick --variant NAME [--nextpnr /path/to/nextpnr-xilinx] \
        [--np-arg=--placer-static-anchor-init --np-arg=20] [--np-opt key=value] [--synth 'yosys cmds'] --run
python3 flow/qor_suite.py vivado --quick --variant NAME --modes placed --run   # Vivado timer on NAME's placements
python3 flow/qor_suite.py report --quick --variant NAME --run                 # build/qor_suite/scoreboard_NAME.md
```

- The variant report has the same tables plus "Variant NAME against base" (Fmax by both timers for the same seeds). The Vivado-alone reference (`--modes free`) does not depend on the variant and is shared; run it once for designs that lack it. `--nextpnr` needs `--variant` (base is the reference flow). Add `--seeds 1 2 3` for a seed sweep instead of seed 1. Without `--run` every step is a dry run that prints what it would do.
